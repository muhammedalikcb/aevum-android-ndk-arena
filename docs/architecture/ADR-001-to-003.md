## ADR-001: Reject `userfaultfd`; build on `mprotect` + `memfd`

Status: Accepted. Date: v1.0. Deciders: Aevum core.

### Context

Our investigation found (see [WHITEPAPER §1](../WHITEPAPER.md)) that ART's CMC
collector services compaction as a per-thread `userfaultfd` (uffd) SIGBUS
demand-fault storm. The obvious first design was to use the *same* mechanism:
register Aevum's own moving space with uffd and service the faults in-process, or
even intercept ART's faults, to get demand-paged relocation and lazy pointer
swizzling (Wilson-style swizzling at page-fault time).

That design cannot be built from an unprivileged Android app. There are three
independent reasons, and any one of them is fatal:

1. Seccomp. The zygote applies a seccomp-bpf *allowlist* to app processes,
   generated from bionic `SYSCALLS.TXT` + `SECCOMP_ALLOWLIST_APP.TXT`.
   `userfaultfd` is not on it: a direct `syscall(SYS_userfaultfd, …)` raises
   `SIGSYS` and the process is killed. ART reaches uffd only through a privileged,
   allowlisted platform path that app code does not share.
2. Kernel sysctl. Even where a bionic path exists, vendors ship
   `vm.unprivileged_userfaultfd = 0`, which restricts uffd to
   `CAP_SYS_PTRACE`/root.
3. Single-owner VMA. uffd registration is exclusive per VMA: a second
   `UFFDIO_REGISTER` over ART's moving space returns `EEXIST`/`EBUSY`. An app
   cannot attach to, observe or pre-service ART's compaction faults.

### Decision

Do not use `userfaultfd` anywhere in Aevum. Provide the two capabilities it would
have given with syscalls the app sandbox permits:

* Backing and persistence: `memfd_create` (+ `F_SEAL_SHRINK|F_SEAL_GROW`) or a
  private file, mapped `MAP_SHARED`. Confirmed allowed for `untrusted_app`.
* Fault-driven page servicing (the incremental-checkpoint dirty tracker):
  `mprotect(PROT_READ)` over live pages, plus a chained `SIGSEGV`/`SIGBUS` handler
  that records the dirtied page and unprotects it with one `mprotect`. `mprotect`
  and `sigaction` are both reachable from an app. The handler is
  async-signal-safe: for a fault inside an Aevum range it does atomic updates and
  a single `mprotect` and nothing else. It does not save and restore `errno`;
  `mprotect` only sets it on failure.

### Consequences

* Positive: the whole engine runs in a stock, unrooted app process, with no
  platform signature, no blocked syscall and no SELinux denial.
* Positive: persistence is *stronger* than a uffd-tmpfs scheme would give. A
  private file survives a device reboot, not only process death.
* Negative: no lazy, demand-paged swizzling. Aevum does not need it. Self-relative
  pointers make reattach O(1) *without* any swizzle (WHITEPAPER §2.1), so the
  capability uffd would have bought is unnecessary, not just unavailable.
* Negative: the dirty tracker's write-protect faults add a first-touch cost per
  page per epoch. That is why it is opt-in and falls back to a full-region flush.

### Validated reachability (what the feasibility recon confirmed)

`ALLOWED`: `memfd_create`, `madvise`, `mprotect`, `mlock` (RLIMIT-bounded), `futex`,
`sched_setaffinity` (cpuset-intersected), `clock_gettime`, LSE atomics, `cntvct_el0`
(EL0-readable), `/sys/devices/system/cpu/**` (readable). `BLOCKED`: `userfaultfd`,
`io_uring_*`, `perf_event_open`, `bpf` (SELinux `neverallow`).

This is what the recon found reachable, not the list of calls the engine makes.
The engine itself uses `memfd_create`, `mmap`, `mprotect`, `msync`, `sigaction`
and `sched_setaffinity`, plus LSE atomics. It does not call `madvise`, `mlock` or
`futex`.

## ADR-002: Reject JVM root scanning & reflection; register field offsets

Status: Accepted. Date: v1.0. Deciders: Aevum core.

### Context

A moving collector must (a) enumerate the live roots and (b) find the reference
fields inside each object, to trace them and to fix them up after a move. ART does
this with JVM stack maps, the runtime root set, and object type metadata or
reflection. Aevum's objects live in a native arena that ART does not know about, so
none of that machinery applies. There were two candidate designs:

1. Mirror the JVM. Track Java object identity into the arena, walk the JVM roots,
   and use reflection to discover fields. This fails at the root: a Java object's
   identity is a heap address that the GC may move and that is destroyed at process
   death, so it cannot be *the* stable identity of a persistent,
   position-independent object. Reflection over JVM types also cannot describe the
   *native* arena layout, and it would tie the on-disk format to JVM class shapes.
2. Own the object model. Give the arena its own object identity (a base-relative
   offset) and its own minimal type descriptor.

### Decision

Aevum owns the object model. Object identity is a base-relative `MRef`
(position-independent, persistent). Each type is described by the byte offsets of
its reference fields plus a fixed payload size, registered once through
`TypeRegistry::registerLayout(type_id, offsets, count, size)`. A single generic
tracer walks those offsets to mark, re-base and fix up. There is no reflection and
no per-type native trace code. Roots are an explicit, durable 32-slot table that
the app sets. The `type_id` is the only type information persisted in each object
header.

```
Kotlin:  ManagedHeap.registerType(typeId=1, refFieldOffsets=intArrayOf(8), sizeBytes=64)
Native:  TypeRegistry::registerLayout(1, {8}, 1, 64)  →  generic offset-walking tracer
```

### Consequences

* Positive: the app describes a type in one line of Kotlin, with no JNI trace
  callbacks. This reflection-free path is what makes the managed heap usable from a
  JVM language.
* Positive: the persisted format depends only on `{type_id, offsets, size}`, not on
  JVM class identity, so a region written by one build attaches in another.
* Positive: no JVM stack scanning ⇒ no safepoint on the *JVM* side ⇒ no coupling to
  ART pauses, which is the point of this design.
* Negative: local `MRef`s are not roots. A compaction that moves an object
  invalidates bare `MRef`s held only in local variables, and the app must re-derive
  them from a root. This is the standard managed-runtime contract, made explicit in
  the API (`WriteScope`, "don't cache a ref across `compact()`").
* Negative: types are fixed-size (offsets and size are static). Variable-size data
  is composed from fixed nodes or lives in the raw arena.

## ADR-003: Prefer ARMv8.1 LSE atomics over hand-rolled CAS retry loops

Status: Accepted. Date: v1.0. Deciders: Aevum core.

### Context

Aevum's hot concurrent primitives (the allocator's Treiber heads, the bump
pointer, forwarding installation, the ragged-safepoint flags) are single-word
atomic updates exercised by up to 64 mutator threads plus the compactor. There are
two ways to implement them:

1. LL/SC CAS retry loops (`ldxr`/`stxr`), the classic lock-free idiom. With many
   cores and cross-cluster contention, `stxr` can fail repeatedly, and a single
   thread's retry loop has no per-operation progress bound: one thread can be
   starved for an arbitrarily long time while others win. Unrelated events also
   clear the exclusive monitor, which makes failures more frequent on big.LITTLE.
2. ARMv8.1 LSE atomics (`cas`/`casal`, `swp`, `ldadd`, …). A *single* instruction
   performs the read-modify-write in the interconnect or near memory. Each
   operation completes in a bounded number of steps regardless of contention
   (wait-free per operation), and fairness under many-core pressure is better.
   LSE is universal on Android 14/15-class SoCs (Cortex-A55/A7x and later, 2018
   onward). The arm64 build enables it at compile time; there is no runtime
   dispatch.

### Decision

Target `-march=armv8-a+crc+lse` and express every hot read-modify-write as a
`std::atomic` operation that lowers to a single LSE instruction, not as a
hand-written CAS loop:

* Forwarding install: `compare_exchange_strong(fwd, 0, D)` → `casal`
  (winner-take-all; see WHITEPAPER §3.3 for why CAS and not `swp`).
* Ragged-safepoint / in-flight flags: `fetch_add`/`fetch_sub` → `ldaddal`.
* SATB rings: single-producer/single-consumer with release/acquire indices, and no
  CAS at all on the write-barrier path (the per-thread ring removes the
  shared-head contention entirely).
* Allocator Treiber heads and the bump cursors (`live_bump`, the managed
  `live_alloc`): a `compare_exchange_weak` loop remains where the algorithm is
  inherently optimistic (pop/push must retry when the head really changed, and the
  bump must check the space bound), but each attempt is a single `casal`, and the
  packed 16-bit ABA tag bounds spurious retries on the Treiber heads.

The software CRC32C and the generic atomics are compile-time fallbacks. They are
used by builds compiled without these extensions (the `armeabi-v7a` library and
the host test builds) and give bit-identical results.

### Consequences

* Positive: no unbounded CAS starvation on the mutator path at 32 or 64 threads;
  the measured scaling (WHITEPAPER §6.2) reflects this.
* Positive: the barrier on the hottest path (SATB) uses no CAS at all. The
  per-thread SPSC ring matters more here than the instruction choice.
* Negative: the `arm64-v8a` library requires ARMv8.1. It is compiled with LSE and
  CRC enabled and has no runtime fallback, so it will not run on an ARMv8.0-only
  core. This is acceptable because the engine targets Android 14/15-class
  hardware.
* Negative: LSE does not remove *contention itself*. It bounds the steps per
  operation, but a single hot line still serializes. Aevum's answer to contention
  is structural (per-thread SATB, per-class free lists, cache-line isolation), with
  LSE as the per-operation guarantee underneath.
